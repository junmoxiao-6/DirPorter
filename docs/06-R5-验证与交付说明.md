## 2. 性能实测

方法：`tests/bench-scan.ps1` 生成真实目录树，跑 `dirporter scan --json`，用 `Start-Process` 轮询
`PeakWorkingSet64` 采峰值内存；条目数用系统 `dir /s /b` 对账。**不靠自证**。

<!-- BENCH_RESULTS -->
### 2.1 正式验收：100,000 个文件 / 400 个子目录（本机 NVMe）

命令：`.\tests\bench-scan.ps1 -Files 100000 -Dirs 400`

| 指标 | 实测 | 阈值 | 余量 |
|---|---|---|---|
| 文件数对账 | `dir` 100000 = DirPorter **100000** | 必须相等 | ✅ |
| 子目录对账 | `dir` 400 = DirPorter **400** | 必须相等 | ✅ |
| 遍历错误 | **0** | 0 | ✅ |
| **扫描挂钟耗时** | **2.25 s** | ≤ 30 s | **13×** |
| **扫描内部计时** | **1356 ms** | — | — |
| **峰值内存** | **34.7 MB** | < 300 MB | **8.6×** |
| 单线程耗时（对照） | 4.10 s | — | 并行加速 **1.82×** |
| 单线程峰值内存 | 33.6 MB | — | — |

（生成 10 万文件的耗时是 236.6 s ≈ 2.37 ms/文件 —— 环境里"造文件"比"扫文件"慢两个数量级，
所以脚本把生成耗时与扫描耗时分开报，避免误读。）

### 2.2 小规模冒烟：1,500 文件 / 30 目录

| 指标 | 实测 |
|---|---|
| 扫描挂钟 | 0.91 s（内部计时 135 ms） |
| 峰值内存 | 30.6 MB |
| 条目数对账 | `dir` 1500/30 = DirPorter 1500/30 ✅ |

小规模下挂钟与内部计时差距明显（0.91s vs 135ms），差值主要是 .NET 进程启动 + JSON 序列化 ——
这正是脚本同时报两个数字的原因。

### 2.3 峰值内存为什么与规模几乎无关

100,000 个文件时峰值 34.7 MB，1,500 个文件时 30.6 MB，增幅不到 5 MB。
这印证了 §2 末尾列出的设计：**内存占用由进程与最宽一层目录决定，而不是由文件总数决定**。


关键设计（为什么内存能压在 300MB 以下）：

1. **聚合而非收集**：默认只累加计数/字节，条目本身不进内存（`ScanOptions.CollectEntries` 才收集）；
2. **层序并行 BFS**：内存是 O(最宽一层的目录数)，与总条目数无关；
3. **单次系统调用拿完整条目**：`FindFirstFileExW` + `FindExInfoBasic` + `FIND_FIRST_EX_LARGE_FETCH`，
   只有压缩/稀疏文件才多调一次 `GetCompressedFileSizeW`；
4. **相对路径每目录只算一次**：逐文件调用 `Path.GetRelativePath` 在 10 万文件时是明显的性能黑洞；
5. **昂贵探测有预算**：硬链接数/ADS 超过上限即降级，并如实置 `DeepProbeSkippedForScale`。

## 3. 两路独立对账（R5 的主要证据形式）

### 3.1 与另一份独立实现（`TreeProbe`）比同源结果

`DirectoryScanner` 与 `TreeProbe` **刻意保留为两份独立实现**（一个层序并行、一个深度优先单线程）：
TreeProbe 的语义已被 R2/R3 大量用例锁定，不应为了复用而改写它。
两者互为对照——用例断言同源的 `FileCount` / `DirectoryCount` / `LogicalBytes` / `DiskBytes` / `MaxFileBytes` 完全一致。
如果哪天其中一份改坏了，这条断言会立刻失败；把其中一个改成另一个的薄封装则会**失去这份交叉验证**。

### 3.2 与系统 `dir` 命令对账

用例 `与系统dir命令对账_条目数一致` 直接调 `dir /s /b /a-d` 与 `dir /s /b /ad` 取条目数，与扫描结果逐个比对。
外部口径印证，避免"自己和自己对账都对"。

### 3.3 安全红线（沿用 /XJ 语义）

`不深入重解析点_但计入重解析点数量`：源内放一个 Junction 指向 500KB 的外部目录，
扫描结果必须是「1 个文件 / 0 个子目录 / 1 个重解析点 / 4 字节」，且**外部数据毫发无损**。
即：链接被识别、被计数、被标注，但**绝不进入**。

## 4. `ScanEstimateCache`：把局限写成可执行断言

### 4.1 有效性与局限

NTFS 语义：**在目录里增 / 删 / 改名条目会更新该目录的修改时间**；
但**修改文件内容或大小不会**。因此目录级缓存：

| 对象 | 是否可靠 | 原因 |
|---|---|---|
| 目录的条目集合（有哪些文件/子目录） | ✅ 可靠 | 增删改名都会改目录 mtime |
| 文件大小 / 字节数 | ❌ **不可靠** | 文件被改写，父目录 mtime 不变 |

用例 `文件内容变化不会让目录级缓存失效_因此只能用于估算` 把这条局限固定下来：
改写同名文件后，缓存**仍然命中**并报出过期字节数，而实时扫描给出真相（9200 字节）。
测试里同时断言 `ScanEstimateResult.ValidityCaveat` 非空——**拿到估算结果的人必须同时拿到这条警告**。

### 4.2 因此设下的硬约束

- 缓存**默认关闭**（`--estimate` 才启用），且**严禁**接入 PRECHECK、复制后校验、目标空间复检等任何影响决策的路径；
- CLI 在 `--estimate` 输出里强制打印有效性说明，JSON 里带 `isEstimate: true` 与 `caveat` 字段；
- 缓存文件损坏时**不抛异常**，按空缓存处理（缓存绝不能影响主流程）；
- 命中时仍要 `stat` 一次目录拿 mtime 做校验，省下的是"枚举内容 + 逐文件系统调用"。

## 5. Restart Manager 深化

### 5.1 结束进程护栏（`CanKill`）

结束进程是本工具里最不可逆的动作，因此"什么情况下必须拒绝"比"能不能杀"更值得被测试：

| 拒绝原因 | 触发条件 | 默认 |
|---|---|---|
| `SystemCritical` | PID 0/4；或进程名命中关键组件表（lsass / csrss / svchost / wininit / services / dwm …） | 恒拒绝 |
| `SelfOrAncestor` | 就是本工具自身 | 恒拒绝 |
| `Shell` | `explorer.exe` | 拒绝，可用 `KillPolicy.AllowShell` 显式放开 |
| `Service` | 报告里带服务短名 | 拒绝，可用 `KillPolicy.AllowServices` 显式放开 |
| `Gone` | 进程已不存在 | 拒绝 |
| **`IdentityMismatch`** | **PID 与实际进程创建时间不符（PID 复用）** | 恒拒绝 |

`IdentityMismatch` 是这轮最有价值的一条：**只凭 PID 去结束进程是危险的**。
Windows 会复用 PID，一个过期的 PID 可能指向完全无关的新进程；报告里记录的进程创建时间
（`RmUniqueProcess.ProcessStartTime`）与 PID 一起构成身份，结束前复核一次即可挡掉这类误杀。
`TryKill` 在真正 `Kill()` 之前还会再复核一次，覆盖"判定与执行之间的竞态窗口"。

引擎侧同步收紧：`OCCUPANCY_SCAN` 现在**先过护栏再结束**，拒绝对原因（含 `[KillRefusal]` 标签）写入台账。

### 5.2 把占用定位到具体文件（`FindLockedResources`）

原先只能回答"这个目录被谁占用"。现在按批注册 + 逐批查询，能把范围缩小到某一批文件
（每批附持有进程），用于"从几十个文件里找出罪魁祸首"。上限 `maxResources` 默认 5000，
因为每批一个 RM 会话，不适合全树扫描。

同时修掉了 `RmGetList` 的一个真实缺口：**第二次数数据时若期间又有进程加入，会返回 `ERROR_MORE_DATA`**，
原实现直接当成失败。现在改为重试（最多 4 次，每次拿更大的缓冲）。

### 5.3 真实性验证

不是只测护栏逻辑：用例 `真实占用检测_能报出持有文件的进程` 用 `FileShare.None` 独占打开一个文件，
断言 RM **确实报出了本进程**；`真实占用检测_未被占用时返回空` 则验证不误报；
`按批定位_只报告被占用的批次` 验证批次归属正确。

## 6. 本轮发现

1. **`PeakWorkingSet64` 采样要轮询**：进程退出后无法再取峰值内存，必须在运行时轮询采样，
   否则测出来永远是 0。基准脚本因此在 `while (-not $HasExited)` 里每 20ms 采一次。
2. **小样本下进程启动开销会淹没扫描时间**：1500 文件时挂钟 0.91s、而扫描内部只用了 135ms
   （差值是 .NET 启动 + JSON 序列化）。因此基准脚本同时报"挂钟"与"内部计时"，避免误读。
3. **本机/沙箱环境下"创建文件"的成本远高于"扫描"**：约 2.6–3.5 ms/文件。
   这也是 R5 单元用例规模被刻意收敛的原因——用例验证的是语义，不是吞吐；吞吐交给基准脚本。
