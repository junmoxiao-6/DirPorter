## 3. 系统工具对账证据（验收第 199 行的前置条件）

用系统 `mklink /J` 创建 Junction，再用本实现解析；并用 `fsutil reparsepoint query` 读原始缓冲区：

```
系统 mklink 创建的重解析缓冲区（前 16 字节）：
03 00 00 A0 | 80 01 | 00 00 | 00 00 | BE 00 | C0 00 | B6 00 | 5C 00 3F 00 3F 00 5C 00 43 00 3A 00
ReparseTag  RepDataLen  Rsvd   SubOff  SubLen  PrintOff PrintLen  \     ?     ?     \     C     :
```

| 字段 | 系统实测值 | 本实现写入值 | 结论 |
|---|---|---|---|
| ReparseTag | `0xA0000003` | `0xA0000003` | 一致 |
| ReparseDataLength | `0x0180`(384) = 8 + (190+2+182+2) | 同公式 | 一致 |
| SubstituteNameOffset | `0` | `0` | 一致 |
| SubstituteNameLength | `190` 字节（含 `\??\` 前缀） | 同 | 一致 |
| PrintNameOffset | `192` = SubstituteNameLength + 2 | 同 | 一致 |
| PrintNameLength | `182` 字节（纯 Win32 路径） | 同 | 一致 |
| PathBuffer 首字符 | `\??\C:` | `\??\C:` | 一致 |

- `fsutil reparsepoint query` 输出 `重分析标记值 : 0xa0000003`，与本实现 `Inspect().ReparseTag` 一致。
- `dir /AL` 对本实现创建的链接输出 `<JUNCTION>  OurLink [目标路径]`，与系统创建的完全同形。
- **反向验证（更重要）**：本实现能正确解析**系统创建**的 Junction（此前所有用例都只读自己写出的缓冲区，属自证循环）。

## 4. 本轮的两项实测发现（都会影响后续模块，必须记住）

### 4.1 ⚠️ 硬链接计数在"删除被路由到回收站"的系统上不会下降

实测（Win11 build 22621.4317，本机）：

| 步骤 | NumberOfLinks | `fsutil hardlink list` |
|---|---|---|
| 新建文件 | 1 | 只有自己 |
| 建 1 个硬链接 | 2 | 两个名字 |
| 删除该硬链接后 | **仍为 2**（轮询 2 秒不收敛） | 第二个名字变成了 `C:\$Recycle.Bin\<SID>\$R******.txt` |

结论：删除**不是**被重定向到回收站的（另做了对照实验：单名文件删除后回收站条目数不变、无本文件标记内容）；但**多硬链接文件的删除**在本机上表现为同卷重命名进回收站，MFT 记录被保留，因此名字数不变。

对后续模块的硬约束：
- `linkdir --incremental` 与批量解链**不得**仅凭 `NumberOfLinks` 判断"还剩几个名字"，必须维护工具自己的链接台账（ledger），逐条核对。
- **⚠️ 口径修正（R2 追加，最高优先级）**：**硬链接计数不可信，一律以迁移台账为准。**
  R3 起引入的**迁移台账（Migration Ledger，见 `docs/03-R2-设计与交付说明.md` §4）是本工具唯一的链接权威来源**：
  - 解链（单条 / 批量 / 迁移回滚）**只按台账条目定位要删的 `linkPath`**，不再读取 `NumberOfLinks` 作为判据；
  - `linkdir --incremental` 的"已存在且一致 → 跳过"判定，改用台账 + 实链的 `Inspect` 结果（重解析标签 / 文件标识），而非链接计数；
  - `HardLinkProvider.Delete` 的 `NumberOfLinks > 1` 守卫**降级为最后一道兜底**（挡住"唯一目录项"这一确定性危险），不再是主要判据。
- 单条 `unlink` 的守卫仍然有效，但要在帮助文档里写明它不是充分保护。
- 单元测试不得断言"删一个硬链接后计数变 1"。

## 5. 与设计文档的偏差修正（实现过程中发现的、必须改口径的点）

| 编号 | 设计文档原话 | 实际情况 | 处理 |
|---|---|---|---|
| C1 | "以 `OPEN_REPARSE_POINT\|BACKUP_SEMANTICS` 打开句柄后调用 `RemoveDirectory`" | `RemoveDirectory` 只接受**路径**，不接受句柄，二者无法组合 | 实现为**等价且更严格**的两步：先用 `FSCTL_DELETE_REPARSE_POINT` 剥离标签 → 再对"已变成空目录的壳"调 `RemoveDirectory`。`RemoveDirectory` 对非空目录必然失败，物理上不可能误删数据 |
| C2 | （未提及）FSCTL_DELETE_REPARSE_POINT 的句柄权限 | 仅用 `DELETE` 权限会返回 `ERROR_ACCESS_DENIED(5)` | 改为 `GENERIC_WRITE \| DELETE \| FILE_READ_ATTRIBUTES \| FILE_WRITE_ATTRIBUTES`；仍失败则回退 `RemoveDirectory`/`DeleteFile`（同样不递归），双重保险 |
| C3 | 硬链接 `Inspect` = `NumberOfLinks > 1` | 硬链接具有**对称性**：两侧路径都会被判为 HardLink，无法区分"原始/链接" | 已在 `Inspect` 与测试中显式记录；这是 `Delete` 必须保守拒绝的第二个理由 |
| C4 | ReFS 支持重解析点 | 未验证 | `Win32VolumeResolver` 按"支持"处理并在代码内留 `TODO(verify)-1`，ReFS 场景返回 `OkWithRisk` 提示先干跑 |
| C5 | TODO(verify)-6：PrintName 布局 | **已实测关闭**，见 §3 对账表 | 实现与系统完全一致 |
| C6 | 硬链接解链依据 | R1 实现用 `NumberOfLinks` 作判据；实测证明该计数在"删除被路由到回收站"的系统上不可信 | **R2 起改为以迁移台账为准**（台账是唯一权威来源），`NumberOfLinks` 降级为兜底守卫。详见 §4.1 与 `docs/03-R2-设计与交付说明.md` §4 |
