## 3. PRECHECK 19 条 ↔ 拒绝码 ↔ 建议动作

| # | 检查项 | 拒绝码 | 级别 | 建议动作 |
|---|---|---|---|---|
| 1 | 源存在、是目录 | `SRC_NOT_FOUND` / `SRC_NOT_DIRECTORY` | Blocking | `ChooseAnotherSource` |
| 2 | 源不是重解析点 | `SRC_IS_LINK`（附带解析出的原目标） | Blocking | `OpenExistingTarget` |

| 6 | 源权限（读+删+改父目录） | `SRC_PERMISSION_DENIED` / `SRC_ENUMERATION_FAILED` | Blocking | `RunAsAdministrator` |

## 4. 迁移台账（Migration Ledger）设计 —— 本次新增需求

> 本节为**设计冻结**，**已完成实现**（R3，与状态机 / Journal 同期落地）。实现说明与验证见 `docs/04-R3-验证与交付说明.md`。

### 4.1 定位：台账是回滚的唯一权威来源（SSOT）

| 文件 | 作用 | 权威性 |
|---|---|---|
| `%ProgramData%\DirPorter\migrations.json` | GUI「迁移记录页」的索引，给人看 | 展示用，**不作为回滚依据** |
| **`{batch-id}.jsonl`（台账）** | 逐条目、逐操作的**文件级权威记录** | **回滚/还原的唯一输入** |

两者以 `batchId` 关联。**禁止出现第二套账本**：还原时只读台账；`migrations.json` 若与台账不一致，以台账为准并在日志中记录差异。

### 4.2 格式（约束 1）

- **默认 JSONL**：`<PARKING 同级>\.migbak\.ledger\{batch-id}.jsonl`
  - 第 1 行：批次头（`recordType:"batch"`，含 `batchId` / `startedAt` / `host` / `schemaVersion`）
  - 后续每行：一条 entry（`recordType:"entry"`，自带 `batchId`，便于流式追加、断电可续、任意行可独立解析）
  - 关键步骤事件另追加一行（`recordType:"event"`，`step` + `at` + `status`）→ **台账兼作 Journal 的第二副本**，被强杀后可从台账恢复到"卡在哪一步"
- **条目数 > 1000 → 自动切换 SQLite**：`{batch-id}.db`（表 `batches` / `entries` / `operations`）
  - 判定时机：批次开始时由 `MigrationPlan` 已知条目数；若运行中动态超过阈值，**一次性提升**（导入 JSONL → 生成 db → JSONL 标记 `promoted`，保留不删）
  - 依赖 `Microsoft.Data.Sqlite`（MIT / 微软官方，+约 2MB，需 `IncludeNativeLibrariesForSelfExtract`）
  - **备选（若你拒绝额外依赖）**：纯 JSONL + 分片（每 1000 条一个文件）+ 内存索引，功能等价、查询稍慢
- **同时生成 Markdown 摘要** `{batch-id}.md`：批次概览 + 每条目的源/停车/目标/链接类型/校验结果，供人工阅读与归档

`batchId` 格式：`mig-yyyyMMdd-HHmmss-<6 位随机>`（示例 `mig-20261008-143052-a1b2c3`）。

### 4.3 记录字段（确定版）

批次头：

```json
{
  "recordType": "batch",
  "schemaVersion": 1,
  "batchId": "mig-20261008-143052-a1b2c3",
  "startedAt": "2026-10-08T14:30:52+08:00",
  "completedAt": "2026-10-08T14:31:10+08:00",
  "host": "WORKSTATION"
}
```

每个 entry：**严格采用你给定的字段**，一字不改：

```json
{
  "recordType": "entry",
  "batchId": "mig-20261008-143052-a1b2c3",
  "entryId": "e-01",
  "sourcePath": "C:\\Users\\Alice\\Documents\\ProjectA",
  "parkingPath": "C:\\Users\\Alice\\Documents\\.migbak\\ProjectA_20261008_143052_a1b2c3",
  "targetPath": "D:\\Archive\\Users\\Alice\\Documents\\ProjectA",
  "linkPath": "C:\\Users\\Alice\\Documents\\ProjectA",
  "linkType": "Junction",
  "volumeSource": "C:",
  "volumeTarget": "D:",
  "operations": [
    { "step": "PARK",   "at": "...", "status": "ok" },
    { "step": "COPY",   "at": "...", "status": "ok" },
    { "step": "LINK",   "at": "...", "status": "ok" },
    { "step": "VERIFY", "at": "...", "status": "ok" }
  ],
  "checksumMethod": "xxHash3",
  "checksum": "a3f9c2..."
}
```

补充字段（**新增，向后兼容**，旧解析器忽略即可）：`fileCount`、`totalBytes`、`linkTarget`（链接解析出的绝对目标）、`result`（`done` / `rolled_back` / `failed`）、`error`。

**校验档位命名（用户决策）**：默认档位 `--verify=metadata`（元数据指纹，秒级）；全文哈希档位 `--verify=content`（慢档）。
**Dry-run 必须明确标注**：content 档会把 restore 校验从**秒级拖到分钟级**（2GB/5 万文件量级可能需数十分钟）。

`checksumMethod: "xxHash3"` 的**哈希对象必须写死定义**（否则回滚校验无法复现）：
> `checksum = XxHash3( 按相对路径 OrdinalIgnoreCase 升序拼接的 "<相对路径>|<长度>|<最后写入时间ticks>\n" )`
> 即**元数据指纹**，2GB / 5 万文件可在秒级重算，用于 `restore` 前后的等价性比对。
> 全文内容哈希作为可选项 `--verify-content`（慢，默认关闭）。

### 4.4 保留策略（约束 2）

**长期保留，不做自动清理。** 台账目录**不在** `BackupRetentionService`（备份保留策略）的清理范围内——清理备份绝不删台账。

### 4.5 安全（约束 3）

**不加密、不做 ACL 保护**，按普通文本/数据库文件存储。
**必须明示的风险**（写入 README 与设置页）：台账含完整路径信息（可能包含用户名、目录结构等隐私），本机任何用户可读。若你的使用环境存在多用户共用同一台机器的情况，请自行把 `.ledger` 目录放到受控位置。

### 4.6 落盘时机与归档（约束 4）

| 时机 | 动作 |
|---|---|
| 每个关键步骤完成后 | 追加 `event` 行（PARK / COPY / LINK / VERIFY 的 `at` + `status`） |
| **`LINK_VERIFY` 成功后** | **立即写入完整 entry**（含 operations 时间线 + checksum）——这是台账的权威落盘点 |
| `BACKUP_CLEANUP` | **归档**：把台账复制到归档位置，**绝不随 `.migbak` 一起删除** |
| 归档目标 | `LedgerArchiveMode`：`AlongsideBackup`（默认，随备份保留位置）/ `TargetSide`（目标侧）/ `UserSpecified`（用户指定目录） |
| 归档失败 | 任务标记 `DONE_WITH_WARNING`，就地保留台账副本并在 UI/日志中告警（**不静默丢弃**） |

归档顺序必须是"先复制成功、再删 `.migbak`"，否则会出现"备份没了、台账也没了"的双输局面。

### 4.7 回滚入口（约束 5）

单条与批量回滚**都以台账为输入**：

```
restore(batchId [, entryId])：
  for entry in 台账条目（批量时按 entryId 逆序，避免父子顺序问题）：
    1. Inspect(linkPath) → 必须确证是链接；不是链接则跳过并告警（绝不删非链接）
    2. 删除链接本体（走 ReparsePointRemover，只删链接、不穿透目标）
    3. MoveFileEx(parkingPath → sourcePath)，同卷原子改名（毫秒级）
    4. 校验：sourcePath 是真实目录（非重解析点）、文件数/checksum 与台账一致
    5. targetPath 侧数据默认保留；仅当用户显式要求才清理
    6. 台账追加一条 restore 记录（append-only，不覆盖原记录）
```

- **硬链接场景按台账条目删**（`entry.linkPath` 直接定位），**不再依赖 `NumberOfLinks`**——R1 已实证该计数在"删除被路由到回收站"的系统上不可信（见 §5.1 与 `docs/02-...` §5）。
- 任一步失败 → 停止后续条目，已完成的条目保持"已还原"状态，未完成的给出修复建议（不半途静默）。

### 4.8 版本与兼容

- `schemaVersion` 从 1 开始；**只允许新增字段，不允许改语义/删字段**
- 读旧版本时向前兼容；遇到更高版本 → 只读展示，拒绝执行写入类操作（避免误解释）

## 5. 本轮实测发现（都会影响 R3 及之后）

### 5.1 系统保留设备名会破坏路径解析 API

`GetVolumePathNameW("C:\...\NUL")` 直接失败（Windows 把 `NUL` 当设备解释），导致目标名非法这一"纯字符串问题"被误报为"无法获取卷信息"。
**处理**：把目标叶子名校验**前置到卷解析之前**（`IsValidLeafName`），拒绝码改为准确的 `TGT_NAME_INVALID`。已加 `CON` / `NUL` / `COM1` 三个用例回归。

### 5.2 路径模式里 `*` 与 `**` 必须是两种语义（★ 本轮最重要的 bug 修复）

早期实现把"结尾 `*`"同时当作"单段通配"和"子树"，于是 `C:\Users\*`（本意：只拦用户 Profile 根目录）实际拦下了**整个用户目录树**——包括 `AppData\Local\Temp`，直接导致 35 个用例集体失败。
**修正**：`*` = 恰好一个段；`**` = 子树（结尾）或任意深度前缀（开头）。所有名单规则已改用显式双星号，并留下回归锚点用例 `段内星号_只匹配一个段_不匹配其子目录`。
**教训（对本项目通用）**：名单/通配规则必须用"正例 + 反例"成对测试；只测正例会让"过度匹配"这种最危险的错误（误伤用户数据目录）完全隐形。

### 5.3 `GetCompressedFileSize` 只对压缩/稀疏文件调用

普通文件的"实际占用"与逻辑大小一致，逐文件调用会白白多出 10 万次系统调用。因此 TreeProbe 的策略是：**仅对带 `FILE_ATTRIBUTE_COMPRESSED` / `SPARSE_FILE` 的文件**调用，其余用逻辑大小。语义与需求一致（占用按实际磁盘占用统计），性能满足"10 万文件 ≤30 秒"。

以下为当时的计划（供对照）：

### 原计划

按 `ILinkProvider ✅ → PRECHECK ✅ → 状态机与回滚` 的顺序，R3 交付：

1. **迁移状态机**：`PLANNED → PRECHECK → DRY_RUN → OCCUPANCY_SCAN → TARGET_PREPARE → COPYING → VERIFYING → PARKING → LINKING → LINK_VERIFY → BACKUP_CLEANUP → DONE`，每步显式登记回滚动作
2. **`SafeTreeDeleter`**（遇重解析点只删本体，绝不穿越）——`BACKUP_CLEANUP` 与台账清理都必须复用它
3. **迁移台账实现**（本轮冻结的设计）：JSONL / SQLite 双模式、Markdown 摘要、归档、`restore` 入口
4. **Journal 与中间态恢复**：`{taskId}.json` 先写 `.tmp` 再原子替换；启动时识别 `.migbak` 残留 / 悬空链接 / 半成品目标
5. **Restart Manager 占用检测**（`RmStartSession` / `RmRegisterResources` / `RmGetList`）
6. **复制引擎 A（robocopy）**：`/XJ` 必带、退出码 ≥8 才判失败、UTF-16 日志解析、字节级进度
7. 验证方式：逐步注入失败的回归测试 + 强杀恢复演练 + `restore` 端到端还原

R3 是本项目风险最高的一轮（唯一涉及真实删除与重命名），我会按"先写回滚动作、再写正向动作"的顺序推进，并在交付时给出可直接复现的中断/恢复演练步骤。
