| 项 | 决定 | 说明 |
|---|---|---|
| 语言/运行时 | C# + .NET 8（`net8.0-windows`） | 按需求；见 D2 备选 net9.0 |

| 链接创建 | **全部原生 API**，禁止 `cmd /c mklink` | 错误码解析脆弱、受区域设置影响（需求硬约束） |

## 6. 四种链接：能力矩阵与 `CanHandle` 判定依据

| 模式 | mklink | 创建 API | 判定/ `Inspect` 标签 | 跨卷 | UNC | 相对 | 权限 | 额外空间 |
|---|---|---|---|---|---|---|---|---|
| Junction | `/J` | `DeviceIoControl` + `FSCTL_SET_REPARSE_POINT`，tag `0xA0000003` | 同 tag；`Inspect` 读 `FSCTL_GET_REPARSE_POINT` | 支持 | **不支持** | 不支持（隐式绝对） | 普通 | 极少 |
| 目录符号链接 | `/D` | `CreateSymbolicLink(..., SYMBOLIC_LINK_FLAG_DIRECTORY)`，tag `0xA000000C` | 同 tag + `FILE_ATTRIBUTE_DIRECTORY` | 支持 | 支持 | 支持 | 管理员 **或** 开发者模式 | 极少 |
| 文件符号链接 | 无参 | `CreateSymbolicLink(..., 0)` | tag `0xA000000C`，无目录位 | 支持 | 支持 | 支持 | 同上 | 极少 |
| 硬链接 | `/H` | `CreateHardLink` | **无重解析点**；判据 = 文件的 `NumberOfLinks > 1`（`GetFileInformationByHandle`） | **不支持** | 不支持 | 不支持 | 普通 | 0 |

**硬链接的 `Inspect` 特殊性**：硬链接不是重解析点，`fsutil reparsepoint query` 会报"不是重解析点"。因此 `Inspect` 必须走两路判定：
1. 重解析点分支 → 读 tag 得 Junction / Symlink / Other；
2. 非重解析点分支 → 对文件查 `NumberOfLinks`，`>1` 报 `HardLink`，否则 `None`。
`inspect --json` 输出字段需包含 `numberOfLinks`，否则无法与 `dir /AL` 对账（验收第 199 行要求与 `dir /AL`、`fsutil reparsepoint query` 一致）。

**符号链接方向性陷阱（写入代码注释）**：`CreateSymbolicLink` 的第 2 参是**目标**，第 3 参才是标志；传参顺序颠倒会得到反向链接且不报错。必须有专门测试。

### 6.1 权限能力探测（启动执行一次并缓存）

| 探测项 | 方法 | 失败含义 |
|---|---|---|
| 是否提权 | `OpenProcessToken` + `GetTokenInformation(TokenElevation)` | 未提权 ⇒ 受保护目录读/删受限，UI 顶部提示 |
| `SeCreateSymbolicLinkPrivilege` | `LookupPrivilegeValueW` + `TokenPrivileges` 逐项比对 `SE_PRIVILEGE_ENABLED` | 无 ⇒ 两种 symlink 置灰 |
| 开发者模式 | 读 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock\AllowDevelopmentWithoutDevLicense`（**经 P/Invoke `RegGetValueW`，不用 reg.exe**） | 0/缺失 ⇒ 非提权时 symlink 置灰 |
| 长路径 | `PathNormalizer` 自检 + manifest `longPathAware` | 见 §18 TODO-7 |

UI 硬要求：不可用的模式**置灰并写明原因**，不允许点下去才报错（需求约束 2）。

### 6.2 智能推荐（`--type auto`）

| 场景 | 推荐 | 一句话理由（UI 展示） |
|---|---|---|
| 目录 + 本地固定卷 + 无 UNC/相对需求 | Junction | 兼容性最好，普通权限即可，不消耗额外空间 |
| 目录 + 需要 UNC 目标 或 相对路径 | 目录符号链接 | Junction 不支持 UNC/相对路径 |
| 文件 + 与链接同卷 | 硬链接 | 零额外空间；不同卷无法建硬链接 |
| 文件 + 跨卷 或 目标是 UNC | 文件符号链接 | 跨卷硬链接不存在 |
| 目录迁移场景（状态机内） | 仅 Junction / 目录符号链接；**硬链接不得出现在候选中** | 硬链接不支持目录 |

## 7. 迁移状态机与回滚对照表（核心）

```
PLANNED → PRECHECK →(DRY_RUN 出口)→ OCCUPANCY_SCAN → TARGET_PREPARE
        → COPYING → VERIFYING → PARKING → LINKING → LINK_VERIFY
        → BACKUP_CLEANUP → DONE
任意中间态 + 失败/取消 → ROLLING_BACK → ROLLED_BACK
进程被杀 → 重启由 JournalRecovery 识别 → 待修复
```

| 状态 | 磁盘动作 | 失败/取消时的磁盘状态 | 回滚动作 | 幂等 |
|---|---|---|---|---|
| PLANNED | 无 | 无 | 无 | ✔ |
| PRECHECK | **只读** | 无 | 无 | ✔ |
| DRY_RUN | **零写入**（需求 137 行硬要求） | 无 | 无 | ✔ |
| OCCUPANCY_SCAN | Restart Manager 会话 | 无 | `RmEndSession` | ✔ |
| TARGET_PREPARE | 建目标父目录；建空目标目录 | 目标多出空目录 | 仅当"本步新建且为空"→ `RemoveDirectory`（**非递归**）；否则保留 + warning | ✔ |
| COPYING | 逐文件写目标 | 目标存在部分/全部文件 | `SafeTreeDeleter` 清空目标目录（**仅限 journal 记录为本任务创建的目录，且遇重解析点不穿越**）；源目录**一字节未动** | ✔（重跑=全量重来，robocopy 会按 size+mtime 跳过相同文件） |
| VERIFYING | 只读比对 | 同 COPYING | 同 COPYING | ✔ |
| PARKING | `MoveFileEx(src, src.migbak-<ts>, 0)` 同卷重命名 | src 消失，`src.migbak-<ts>` 存在 | `MoveFileEx` 反向重命名，**毫秒级、零数据风险** | ✔ |
| LINKING | 在原路径建链接 | 链接可能半成品 | 若链接存在 → `ILinkProvider.Delete`（只删本体）；再改回原名 | ✔ |
| LINK_VERIFY | 只读：解析目标 + 枚举子项 + 试读 1 文件 | 链接存在但不可用 | Delete 链接 → 改回原名。目标侧数据保留（用户可选留/删） | ✔ |
| BACKUP_CLEANUP | **删除 `.migbak` 目录树** ← 全局唯一不可逆点 | 部分删除 | 不可逆。**因此置于最后一步**，且删除前强制 `LINK_VERIFY` 通过；提供"保留备份 N 天"开关（需求 95 行） | ✘（失败仅影响磁盘占用，不影响数据） |
| DONE | 写 journal | — | 通过 `restore` 反向执行 | — |

### 7.1 三条必须写进代码注释的安全铁律

1. **Unlink 绝不允许递归删除**：**禁止** `Directory.Delete(path, true)`、`rd /s`、`SHFileOperation`、自研递归遍历。递归会顺着重解析点进目标目录，把真实数据全删光——同类工具最经典的致命 bug。（需求 73 行）
   **R1 实现口径修正（C1/C2）**：需求原文写的是"以 `OPEN_REPARSE_POINT | BACKUP_SEMANTICS` 打开句柄后调用 `RemoveDirectory`"，但 `RemoveDirectory` 只接受路径、不接受句柄，二者无法组合。实际实现为**等价且更严格**的两步：① 以该组标志打开句柄 → `FSCTL_DELETE_REPARSE_POINT` 剥离标签（此调用只改元数据，不触碰数据）；② 对"已变成空目录的壳"调用 `RemoveDirectory` —— 它对非空目录必然返回 `ERROR_DIR_NOT_EMPTY`，因此物理上不可能误删。另实测：`FSCTL_DELETE_REPARSE_POINT` 仅用 `DELETE` 权限会返回 `ERROR_ACCESS_DENIED`，句柄须带写权限；实现中另加了 `RemoveDirectory`/`DeleteFile` 回退路径（同样不递归）。详见 `docs/02-R1-验证与交付说明.md` §5。
2. **`SafeTreeDeleter` 是唯一删除器**：`BACKUP_CLEANUP` 删 `.migbak` 时，`.migbak` 内部**可能含嵌套 Junction**（源目录本身含链接是合法场景）。因此递归删除器必须"遇重解析点只删本体、不穿越"。这条是本设计的原创补充，需求文档未显式提出，但不做就会在 `BACKUP_CLEANUP` 阶段制造同等规模的数据灾难。
3. **先改名再建链，绝不先删源**：`PARKING` 用同卷重命名瞬时腾位，保证 `LINKING` 失败时回滚是"改个名字回去"。

### 7.2 中间态恢复（`JournalRecovery`）

启动时扫 journal 中处于中间态的任务，逐项给出**可执行修复建议**，不自动执行：

| 现象 | 判定 | 建议动作 |
|---|---|---|
| `<src>.migbak-<ts>` 存在 且 `src` 不存在 | 停在 PARKING/LINKING | `[改回原名]` 或 `[重试建链]` |
| `src` 是重解析点 且 `.migbak` 仍存在 | 停在 LINK_VERIFY 之前 | `[确认新位置完整后删 .migbak]` 或 `[删除链接并改回原名]` |
| `src` 完好 且 目标有残留文件 | 停在 COPYING/VERIFYING | `[清理目标残留]` |
| `src` 是重解析点 且 无 `.migbak` | 已完成，日志未落盘 | `[补写完成记录]` |

## 8. PRECHECK 实现映射（19 条，逐条）

判定所需的全部 API 已在 §4 `FileSystem/` 中列出。核心映射：

| # | 检查 | 实现要点 | 不通过行为 |
|---|---|---|---|
| 1 | 源存在且为目录 | `GetFileAttributesW` 位判定 | Blocking |
| 2 | 源不是重解析点 | `FILE_ATTRIBUTE_REPARSE_POINT` + `Inspect` | Blocking，并给"打开目标/还原"入口 |
| 3 | 系统关键目录黑名单 | `BlacklistPolicy` 数据驱动，见 §9.1 | **硬拒绝** |
| 4 | 警告名单 | `WarningListPolicy` | RequireAcknowledge + 二次确认弹窗 |
| 5 | 树内特殊对象 | `FileMetaProbe`：嵌套重解析点 / 硬链接 / 稀疏 / ADS / EFS / 云占位（`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`=0x00400000、`RECALL_ON_OPEN`=0x00040000） / symlink | 逐项 Info/Warning |
| 6 | 源权限 | `GetNamedSecurityInfoW` + 有效访问位；提权后默认可读删 | Blocking |
| 7 | 目标是本地固定卷 | `GetVolumePathNameW`→`GetDriveTypeW == DRIVE_FIXED` | 硬拒绝（`DRIVE_REMOVABLE`/`DRIVE_REMOTE`） |
| 8 | 目标卷 FS 为 NTFS/ReFS | `GetVolumeInformationW` 读 FS 名 | 硬拒绝（FAT32/exFAT） |
| 9 | 防环 | `PathNormalizer.IsSameOrUnder` 双向判定 | 硬拒绝 |
| 10 | 空间 ≥ 源实际占用 ×1.05 | `SpaceCalculator`（`GetCompressedFileSizeW`，非名义大小） | Blocking，零写入 |
| 11 | 目标同名目录 | 非空拒绝；空目录询问复用 | Blocking / 询问 |
| 12 | 目标父目录可写 | ACL 有效写位 | Blocking |
| 13 | 批次嵌套 `A` 与 `A\B` | 前缀关系检测，只迁移 `A` | 自动跳过 `A\B` + UI 说明 |
| 14 | 批次目标冲突 | 目标路径去重（规范化后比较） | Blocking |
| 15 | 批次总占用复检 | 汇总后与目标卷剩余比较 | Blocking |

## 9. 名单与特殊对象策略

### 9.1 黑名单（硬拒绝，数据驱动）

卷根（`X:\`）· `C:\Windows` 及全部子目录 · `System Volume Information` · `$Recycle.Bin` · `C:\Users` · `C:\Users\<user>`（Profile 根）· `C:\Users\Public` · `C:\ProgramData`（仅根本身）· `WinSxS` · `AppData\Local\Microsoft\*` · `AppData\Local\Packages\*` · `AppData\Roaming\Microsoft\*`。
存储为 JSON（`Resources/blacklist.json`），支持路径模板 + 卷根通配；匹配用规范化后的 `\\?\` 路径，且**区分大小写不敏感**、**不跟随重解析点**。

### 9.2 警告名单（需勾选"我理解风险" + 二次确认）

`C:\Program Files` · `C:\Program Files (x86)` · `C:\ProgramData` 下非 Microsoft 子目录 · 杀毒/驱动/Office 相关目录 · 被服务或开机启动项引用的目录（读 `HKLM\SYSTEM\CurrentControlSet\Services\*\ImagePath` 与 Run 键做包含匹配，**只读**）。

### 9.3 特殊对象 → 行为矩阵

| 对象 | 检测 | 默认行为 | 用户可覆盖 |
|---|---|---|---|
| 嵌套 Junction/Symlink | 重解析点属性 | 不递归（`/XJ`），预览中明确标注 | 否（安全） |
| 硬链接文件 | `NumberOfLinks > 1` | 复制为独立文件（数据正确、丢失链接关系），标注 | 是（改为原样保留） |
| 稀疏文件 | `FSCTL_QUERY_ALLOCATED_RANGES` / `GetCompressedFileSize` 差异 | 标注；robocopy 默认处理 | 是 |
| ADS | `FindFirstStreamW` / `FindNextStreamW` | `/COPYALL` 已含 ADS | 否 |
| EFS 加密 | `FILE_ATTRIBUTE_ENCRYPTED` | **标注 + 默认跳过并计入失败**（原因见 TODO-2） | 是（`/EFSRAW`） |
| 云占位文件 | `RECALL_ON_DATA_ACCESS` / `RECALL_ON_OPEN` | 标注"将触发下载"，预览显示"可能下载 N 个文件" | 是（改为只迁移占位符，需 `/COPYALL` 之外的处理，列为 TODO-3） |

## 10. 复制引擎取舍结论：**A（robocopy）为 v1 默认，B 预留接口**

| 维度 | A: robocopy 子进程 | B: 自研多线程 `CopyFileEx` |
|---|---|---|
| ACL / 属性 / 时间戳 / ADS | `/COPYALL /DCOPY:DAT` 开箱正确，十余年边界验证 | 需自实现：`Get/SetNamedSecurityInfoW`、`FindFirstStreamW` 读写 ADS、`SetFileTime` 补创建时间 |
| 稀疏 / EFS / 长路径 / 嵌套链接 | `/XJ` 处理链接环、`/COPYALL` 处理稀疏与 EFS | 全部自担，稀疏要 `FSCTL_SET_SPARSE`，EFS 基本无解 |
| 进度粒度 | 日志逐文件一行（`/BYTES /FP /NC /NDL /NP`），≈文件级字节累计 | 字节级（`CopyFileEx` 进度回调） |
| 暂停/继续 | 只能终止进程；继续=重启（robocopy 按 size+mtime 跳过已完成，实际增量） | 回调返回 `PROGRESS_STOP` 可停，但**无断点续传**，继续仍需重传该文件 |
| 取消 | 终止进程，已复制文件保留 → 走 COPYING 回滚 | 回调 `PROGRESS_CANCEL` 干净退出 |
| 开发量 / 风险 | 低 | 高（元数据正确性是主要雷区） |
| 退出码 | 0–16 语义需仔细解析（0–7 都可能"有内容"） | 自定 |

**结论**：v1 用 A。理由是**本产品的差异化是"校验 + 回滚 + 可观测"，不是复制速度**；元数据正确性的权重远高于进度平滑度。2GB/5 万文件场景下日志行粒度已足够平滑（每 ≈40 KB 一行），配合 UI 节流 ≤10 次/秒完全达标。`IFileCopier` 抽象保证 B 可在 v2 无痛替换。

**robocopy 的 3 个必须做对的细节**：
1. 参数固定：`/E /COPYALL /DCOPY:DAT /R:1 /W:1 /MT:8 /XJ /BYTES /FP /NC /NDL /NP /LOG:<tmp>` + `UNICODE`（否则中文日志乱码）；`/XJ` **必须有**。
2. 退出码 `≥8` 才判失败；`1–7` 需解析日志尾部汇总行判定真实失败数；`0` 且日志含 "ERROR" 也需复核。
3. 源/目标路径带 `\\?\` 传给 robocopy 的行为需实测（TODO-4）；日志以 UTF-16 读取，解析用"字节数字段"而非本地化文本。

## 11. 扫描与内存策略

- **默认 `Win32WalkScanner`**：`FindFirstFileExW` 用 `FindExInfoBasic` + `FIND_FIRST_EX_LARGE_FETCH`，多线程按目录并行；**流式聚合**——只保留目录级聚合节点（大小/文件数/最大文件），文件级仅保留 Top-N 大文件（`PriorityQueue` 固定堆）。稳态内存 < 300 MB。
- **USN 快速扫描（v1 不实现，留接口）**：`FSCTL_ENUM_USN_DATA` 读 MFT 确实最快，但把 `FileReferenceNumber` 还原成完整路径需逐项 `OpenFileById` + `GetFinalPathNameByHandle`，实测成本可能反超目录遍历。列为 TODO-5，v1 不引入未验证的性能承诺。
- **缓存**：`ScanCache` 记录每个扫描根的 USN、最后写入时间、结果快照；二次扫描 USN 未变则秒出（需求 132 行）。
- **UI 不冻结**：IO 全在后台线程（`Task.Run` + `Channel`），UI 只消费聚合进度事件，节流 ≤10 次/秒。

### 10.1 复制引擎 A+B 双实现（依 D1 修订）

- `IFileCopier` 保留两个实现：`RobocopyCopier`（A）、`ManagedCopier`（B，`CopyFileEx` 多线程）。
- 选择方式：设置项 `CopyEngine = Auto | Robocopy | Managed`。
  - `Auto` 判定规则：目标卷为 NTFS + 树内含 EFS/稀疏/ADS 任一 → **A**；纯普通文件且需精确进度 → **B**；无法判定 → **A**（保守）。
  - `ManagedCopier` 必须自担：ACL（`Get/SetNamedSecurityInfoW`）、ADS（`FindFirstStreamW` 读写）、创建时间（`SetFileTime`）、稀疏（`FSCTL_SET_SPARSE`）、重解析点跳过。**首次实现按"普通文件正确 + 元数据尽力保留 + 明确报告能力缺口"交付**，不假装与 A 等价；`CopyCapabilities` 结构体如实声明支持面，UI 上对不支持的元数据给出显式警告。
- 两个实现共用同一 `CopyResult` / `CopyProgress` 契约，进度语义统一为"字节级累计"，A 由日志行累计近似。

### 10.2 权限模式（依 D1 修订）

需求原文要求"manifest 默认 `requireAdministrator` + 提供普通权限降级路径"。为支持"每个复制引擎都能选管理员/普通权限"，增加第三个选项：**本次操作提权**（不改 manifest 的默认值，而是运行时另起提权进程）。

| 模式 | 机制 | 能力 |
|---|---|---|
| 默认（manifest） | `requireAdministrator`，启动即 UAC | 全功能 |
| 降级 | 设置项 `AllowStandardUserMode=true` + `asInvoker` 辅助启动方式，或用户显式以普通权限运行 | 受保护目录读/删失败；符号链接不可用；UI 顶部常驻提示"能力受限" |
| 按需提权（新增） | 以同一 exe 的隐藏子命令 `--elevated-worker` 经 `ShellExecuteW(runas)` 拉起，**提权进程只做单一动作**（复制 / 建链），进度与结果经日志文件回传父进程 tail 读取 | 主进程保持普通权限，仅在必要动作上提权 |

**限制必须写进 README**：提权子进程无法继承父进程的标准输出句柄，因此"按需提权"模式下进度只能经**日志文件中转**（延迟 ≤1s，可接受）；且提权进程一旦启动，取消需经"请求文件 + 子进程轮询"实现，非即时。**默认不使用按需提权**，仅在用户显式选择时启用。

## 20. 备份策略（依 D5 修订，含技术澄清）

### 13.1 为什么 `PARKING` 不能直接搬到统一备份目录

需求原文的状态机设计意图（第 94 行）是：`PARKING` 把源目录**同卷重命名**为 `<name>.migbak-<ts>`，从而"瞬时腾位、毫秒级可回滚、零数据风险"。
若把备份直接搬到另一个位置的统一目录，则：

- 重命名退化为**跨卷复制几十 GB**，"瞬时腾位"消失，`LINKING` 前的窗口期被拉到数十分钟；
- 回滚从"改个名字回去"退化为"再复制一遍回来"，失败面扩大一倍；
- `restore` 也要跨卷搬回，风险叠加。

**因此 `PARKING` 必须保持同卷原地改名，这一点不因 D5 而改变。**

### 13.2 统一备份位置的实际落地方式（满足 D5 的诉求）

D5 的诉求（归集 + 保留天数 + 自动清理）用三层实现，且**不牺牲回滚安全性**：

| 层 | 位置 | 说明 |
|---|---|---|
| ① 就地改名（必须有） | `<源父目录>\<name>.migbak-<yyyyMMddHHmmss>` | `PARKING` 步骤，同卷原子重命名，回滚唯一依赖 |
| ② 统一备份仓（可选，后置） | `%ProgramData%\DirPorter\backups\<taskId>\` | 在 `LINK_VERIFY` **通过之后**新增可选步骤 `BACKUP_RELOCATE`：此时原路径已由链接接管，把 `.migbak` 移入统一仓是安全的。**默认关闭**，开启后回滚代价为跨卷搬回，UI 必须明示 |
| ③ 备份索引与保留策略 | `%ProgramData%\DirPorter\backups\index.json` | `BackupRetentionService` 统一登记所有备份（不管是①还是②），按配置**保留 N 天**（默认 7）自动清理，可选"永不自动清理"。清理前强制校验对应链接健康度 |

- 保留天数、是否自动清理、是否启用②，全部在设置页可改，且可**逐任务覆盖**。
- 自动清理是唯一会删除 `.migbak` 的路径，**必须**复用 `SafeTreeDeleter`（遇重解析点不穿越，§7.1 铁律 2）。
- `BACKUP_CLEANUP` 的语义据此明确为："按保留策略决定是否立即删除；若配置了保留 N 天，则本步只登记不删除，交由 `BackupRetentionService` 到期清理。"

**待你最终确认的一点**：②统一备份仓 **默认关闭 / 默认开启**？我建议**默认关闭**（保留①的就地改名位置，回滚最快），开启后按 §13.2 明示代价。若你希望"所有备份必须集中一处"，我改为默认开启并在 Dry-run 中显著标注"回滚需跨卷搬回、耗时较长"。

## 21. R1 实测环境发现（影响后续模块，必须遵守）

### 21.1 ⚠️ 硬链接计数在"删除被路由到回收站"的系统上不会下降

实测（本机 Win11 build 22621.4317）：

| 步骤 | `NumberOfLinks` | `fsutil hardlink list` |
|---|---|---|
| 新建文件 | 1 | 只有自己 |
| 建 1 个硬链接 | 2 | 两个名字 |
| 删除该硬链接后 | **仍为 2**（轮询 2 秒不收敛） | 第二个名字变成 `C:\$Recycle.Bin\<SID>\$R******.txt` |

对照实验证明**不是**本项目代码或 P/Invoke 的问题：单名文件删除后回收站条目数不变、且找不到本文件内容（即普通删除确实是永久删除）；`fsutil` 与我们的 `GetFileInformationByHandle` 读数**完全一致**。

对后续模块的硬约束：
- `linkdir --incremental` 与批量解链**不得**仅凭 `NumberOfLinks` 判断"还剩几个名字"，必须维护工具自己的链接台账（ledger），逐条核对后再删；
- 单条 `unlink` 的 `NumberOfLinks > 1` 守卫仍然有效（挡住"唯一目录项"这一确定性危险），但**不是**充分保护，README 与 UI 必须写明；
- 单元测试**不得**断言"删一个硬链接后计数变 1"。

### 21.2 硬链接的对称性

硬链接不是重解析点，两侧路径指向同一 MFT 记录，`Inspect` 对**两侧都会报告 `HardLink`**，无法区分"原始文件"与"链接"。这是 `Delete` 必须保守拒绝（链接数 ≤ 1 时拒删）的第二个理由。批量场景必须靠自维护台账知道"哪些名字是本工具建的"。

### 21.3 本机开发环境限制

- 未提权且未开启开发者模式 → 两种符号链接的真实创建分支在本机无法执行；测试已设计为"两条分支都断言"（无权限时断言明确的权限拒绝，而不是跳过）。
- 编译需读取 `C:\Program Files\dotnet\packs` 参考程序集，在沙箱内被拒绝 → 本机跑 `dotnet build/test` 需放行（用户自行在终端执行不受影响）。
- `reg.exe` 被安全策略拦截 → 一切注册表读取走 P/Invoke `RegGetValueW`。

### 21.4 R2 新增发现（详见 `docs/03-R2-设计与交付说明.md` §5）

1. **`*` 与 `**` 必须是两种语义**：早期把"结尾 `*`"同时当作单段通配与子树，导致 `C:\Users\*` 拦下整个用户目录树（含 `AppData\Local\Temp`），35 个用例集体失败。修正为 `*` = 一个段、`**` = 子树/任意深度。**名单类规则必须成对做正反用例测试**，否则"过度匹配"这种最危险的错误会完全隐形。
2. **系统保留设备名会破坏路径解析 API**：`GetVolumePathNameW` 对 `...\NUL` 直接失败 → 目标叶子名校验必须前置，否则"名字非法"被误报为"卷不可用"。
3. `GetCompressedFileSize` 只对压缩/稀疏文件调用（普通文件逻辑大小 == 实际占用），否则 10 万文件会白白多出 10 万次系统调用。

### 21.5 R3 新增发现（详见 `docs/04-R3-验证与交付说明.md` §5）

1. **⚠️ `/COPYALL` 在非管理员下让 robocopy 直接返回 16（一个文件都不复制）**：`/COPYALL` 含 `U`（审计 SACL），需要 `SeSecurityPrivilege`。非提权时必须改用 `/COPY:DATSO`，否则普通权限下**核心迁移流程 100% 不可用**。已实现按权限选择 + 检出 16 自动降级重试，并在结果中写明降级说明。
2. **⚠️ 恢复分析必须"终态优先"**：迁移成功后停车目录按策略保留属于设计行为，若只看磁盘特征（源是链接 + 停车目录存在）会把它误报为待处理的**破坏性**建议，诱导用户误删备份。已改为：Journal 终态只判"磁盘是否与记录一致"；中间态即便无风险也要上报但不计入"待处理"。
3. **安全关键代码只允许一份实现**：`ReparsePointRemover` 与 Links 内的删除逻辑合并到 `FileSystem/ReparsePointOps.RemoveLinkBody`，`NativeLinkHelper` 退化为薄委托，分层为"FileSystem = 原语 / Links = 语义"。
4. **`DIRPORTER_DATA_ROOT`**：新增数据根目录环境变量覆盖，既支持便携模式，也让演练/测试完全隔离（否则演练会污染真实 Journal 导致判定不确定）。

### 21.6 R4 新增发现（详见 `docs/05-R4-验证与交付说明.md` §4）

1. **⚠️ robocopy 的 `/LOG` 文件是系统 ANSI 单字节编码，不是 UTF-16**：`/UNICODE` 只影响控制台。原实现按 UTF-16 读日志，导致**引擎 A 的"已复制文件数/字节数"与进度长期恒为 0**，中文错误行也检不出。修复：新增 `AnsiText`（`MultiByteToWideChar(CP_ACP)`，含 BOM 识别），计数改为以日志末尾**汇总块**为权威来源（只判断行末 6 个 token 是否都是整数，与本地化文案无关）。
2. **⚠️ `DllImport` 默认按 ANSI 编组 `char[]`**：`MultiByteToWideChar` 未声明 `CharSet.Unicode` 时会把 `char[]` 当 1 字节写，输出全为 NUL。已在代码中显式声明并加注释防回退。
3. **⚠️ PowerShell 5.1 + `$ErrorActionPreference='Stop'` + 原生命令写 stderr = 空消息终止性异常**：CLI 进度写在 stderr，测试脚本必然踩到。修复：调用原生命令时局部降级为 `Continue`，`move` 加 `--quiet`。
4. **⚠️ `.ps1` 必须带 UTF-8 BOM**：PS 5.1 对无 BOM 脚本按系统 ANSI 解码，中文会变乱码并引发语法错误（提权脚本首次运行即因此失败）。仓库内三个脚本已统一加 BOM。
5. **`SeRestorePrivilege` / `SeSecurityPrivilege` 在管理员令牌里默认是 disabled**："持有"不等于"已启用"，写所有者/SACL 前必须 `AdjustTokenPrivileges` 显式启用，否则返回 1314。已实现 `TokenPrivilegeEnabler`。
6. **`CopyFileEx` 不复制安全描述符**（文档化行为），但**会逐流复制 ADS**（已实测确认）；稀疏则会被"填实"，必须自己用 `FSCTL_SET_SPARSE` + `FSCTL_SET_ZERO_DATA` 还原，且置零前必须确认该区域全零（已实现安全阀）。

### 21.7 R5 新增发现（详见 `docs/06-R5-验证与交付说明.md`）

1. **⚠️ 目录级缓存对"文件内容变化"无效**：NTFS 里增/删/改名条目会更新目录 mtime，但**修改文件内容不会**。因此按目录 mtime 键控的缓存只能可靠复用"条目集合"，字节数会过期。`ScanEstimateCache` 据此定位为**仅供预览估算**（默认关闭），并把这个局限写成可执行断言（`文件内容变化不会让目录级缓存失效_因此只能用于估算`）。**严禁接入 PRECHECK / 校验 / 空间复检**。
2. **⚠️ 只凭 PID 结束进程是危险的**：Windows 会复用 PID。报告里记录的进程创建时间（`RmUniqueProcess.ProcessStartTime`）与 PID 一起构成身份，结束前必须复核（`KillRefusal.IdentityMismatch`），且 `Kill()` 前再复核一次以覆盖竞态窗口。
3. **`RmGetList` 第二次数数据时可能返回 `ERROR_MORE_DATA`**（期间有新进程加入），原实现直接判失败 → 改为重试（最多 4 次，逐次加大缓冲）。
4. **`PeakWorkingSet64` 必须在进程运行时轮询采样**：进程退出后取不到峰值（会读成 0）。
5. **扫描的内存与时间都要靠"聚合而非收集"**：默认不把条目放进内存；相对路径每目录只算一次（逐文件 `Path.GetRelativePath` 是 10 万文件量级的性能黑洞）。
6. **本机环境实测：创建文件约 2.6–3.5 ms/个，远慢于扫描本身**。因此扫描基准以挂钟 + 内部计时双报，避免把 .NET 启动开销误读成扫描耗时。

### 21.8 R6 新增发现（详见 `docs/07-R6-完整CLI与单文件发布.md` §7）

1. **⚠️ XML 注释里不能有两个连续的连字符** —— 清单注释里写了命令行参数（双连字符形式）→ 清单非法 →
   **exe 完全无法启动**，报"应用程序的并行配置不正确"（SxS 无法生成激活上下文）。
   最坑的是**编译完全不报错**。已重写清单并新增用例 `R6_CliTests.应用清单_必须是合法XML_且注释里不能有双连字符` 兜住。
2. **`$ErrorActionPreference = "Stop"` 会把清理失败升级成终止错误**：`publish.ps1` 因此打印完标题就退出，看起来像发布失败。清理步骤现在 `try/catch` 包裹且失败不阻断发布。
3. **裁剪发布实测不可用**：`-Trim` 体积 11.6 MB（未裁剪 34.7 MB），但会关闭 `JsonSerializerIsReflectionEnabledByDefault`，所有 `--json`/台账/Journal 的反射式 JSON 全部失效，`selfcheck` 直接失败。要用裁剪必须先做 `JsonSerializerContext` 源生成改造；当前默认关闭，并以 `selfcheck` 作为硬闸门。
4. **"发布成功"≠"发布出去的能跑"**：因此新增 `selfcheck` 命令（覆盖权限、robocopy、数据目录、JSONL+SQLite 两种台账后端往返、链接能力矩阵），`publish.ps1` 发布后强制执行。
5. **单文件发布必须带 `IncludeNativeLibrariesForSelfExtract=true`**，否则 `Microsoft.Data.Sqlite` 的原生 `e_sqlite3` 在"条目 >1000 切 SQLite"这条路径上会静默失效。
6. **权限清单的一次显式偏离**：需求要求"默认 requireAdministrator + 同时提供普通权限降级路径"，但单 exe 里二者不可兼得（写了 requireAdministrator 就无法在同 exe 内降级，且只读命令也会弹 UAC）。本项目默认 `asInvoker`（按需提权），另提供 `app.admin.manifest` 变体由 `publish.ps1 -RequireAdmin` 切换。

### 21.9 R7 新增发现（详见 `docs/08-R7-GUI与单文件发布.md` §5）

1. **⚠️ WPF 的 pack URI 里写的是「程序集名」，不是命名空间**。本项目程序集名是 `dirporter`（`RootNamespace` 才是 `DirPorter.App`），
   于是 `pack://application:,,,/DirPorter.App;component/Themes/Light.xaml` 在运行期抛 `FileNotFoundException: Could not load file or assembly 'DirPorter.App'`，
   主题字典加载失败 → **界面丢掉全部配色**。已改为运行时反射取程序集名（改名也不会再踩），并把主题加载降级为"失败不影响启动"。
   **发现方式值得记下**：GUI 启动看起来完全正常，是去翻 `%ProgramData%\DirPorter\crashes\` 才抓到的——
   非致命异常必须有主动查日志的习惯，否则"界面能打开"会掩盖问题。
2. **界面契约必须靠「静态扫描 + 真实实例化」两条腿**。XAML 的绝大多数错误（资源键写错、本地化键漏定义、
   注释里出现非法双连字符、`StaticResource` 找不到）**编译期完全不报错**，只有真的把那个页面 `new` 出来才会炸。
   已落成 10 个用例（`R7_XamlContractTests`），其中最后一个是**在 STA 线程上真实构造五个页面 + 主窗口 + 切换主题**。
3. **测试必须复刻生产路径**。契约测试初版用裸 `new Application()` 建宿主，五个页面**集体**抛「无法找到 `PageTitle` 资源」——
   因为裸 `Application` 不会加载 `App.xaml` 的 `Application.Resources`。生产路径走 `App.InitializeComponent()` 是对的，
   但测试若不复刻，测的是个假环境。已修正。
4. **WinExe 让 PowerShell 不等待、也拿不到退出码**。`& dirporter.exe selfcheck` 在 PowerShell 里既不等进程也不设 `$LASTEXITCODE`，
   发布脚本的"发布后自检"因此形同虚设。必须改用 `Start-Process -Wait -RedirectStandardOutput`。
5. **WPF 单文件实测 64.5 MB**（R6 曾预估 150–180 MB，因为漏算了 `EnableCompressionInSingleFile` 的压缩效果）。
   运行期工作集：Debug 约 59 MB，自包含单文件首次运行约 223 MB —— 均低于"稳态 < 300MB"的非功能要求。

### 21.10 R8 新增发现（详见 `docs/09-R8-界面体验修复.md`）

1. **⚠️ "从集合里移除选中项"是双向绑定的经典陷阱**。`Roots.Remove(SelectedRoot)` 会让 `ListBox.SelectedItem` 变 null，
   绑定立刻把 null 回写 → 紧接着读 `SelectedRoot.IsPreset` 就空引用。用户实测崩溃日志实证。
   **规则**：处理选中项的移除时，先取局部变量，后续一律用局部变量，并主动清空选中。
2. **⚠️ Auto 行会吃光 `*` 行**。迁移页 4 个 Auto 区合计约 640px，在 780px 窗口里把队列区挤到只剩 ~45px
   （只看得见表头）。**规则**：主列表所在行必须给 `MinHeight`，窗口 `MinHeight` 必须能容纳完整页面；
   默认折叠的大块预览不要放在 Auto 行里当作"随手打开"。
3. **WinExe 的标准输出句柄不能盲目包 `FileStream`**。在 MSYS/Git Bash 与部分 CI 的管道上会抛异常；
   若这段代码在 `try` 之外，整个进程崩溃并打印 .NET 堆栈。
   **规则**：优先 `Console.OpenStandardOutput()`，句柄包装只做兜底，且这条路径**永不抛**。
4. **测试会污染用户数据目录**。`DirPorterPaths` 是进程级静态的，凡走 Journal / 迁移记录的用例都在往
   `%ProgramData%\DirPorter` 写。已用 `[ModuleInitializer]` 在**任何测试之前**把 `DIRPORTER_DATA_ROOT`
   指向临时目录；共享数据根的用例再用显式串行集合 + 用后还原。
5. **测试套件耗时可能被环境主导**。本轮套件从 ~8s 变到 3–4.5 分钟，A/B（数据根指回 ProgramData）同样是 3m25s，
   且慢的是 R2 TreeProbe / R3 Ledger / R5 Scan 这类**纯文件 IO、与改动无关**的用例 →
   属当前机器文件 IO 负载（Defender / 磁盘占用 / 同时段其它进程），不是回归。

### 22.1 迁移台账（Migration Ledger）—— 新增需求，设计已冻结

回滚的**唯一权威来源**。默认 JSONL（`<PARKING 同级>\.migbak\.ledger\{batch-id}.jsonl`），条目 >1000 时切 SQLite，同时产出 Markdown 摘要；**长期保留、不自动清理**；不加密、不做 ACL 保护；**在 `LINK_VERIFY` 成功后立即写入**，随 `BACKUP_CLEANUP` 归档，**绝不随 `.migbak` 一起删除**；单条/批量回滚都以台账为输入，**硬链接解链按台账条目删，不再依赖 `NumberOfLinks`**。

完整字段定义、写入时机、归档策略与回滚流程见 **`docs/03-R2-设计与交付说明.md` §4**。
